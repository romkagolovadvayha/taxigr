# Диагностика отказа RuStore: 1.0.7 (22)

Проверено 7 сентября 2026 года. Модератор сообщил об ошибке 502 после ввода
тестового номера на Android 15, Xiaomi 2306EPN60G.

**Причина серверного простоя установлена по production-логам и исправлена.**
Автообновление MySQL остановило зависимый API через `Requires=mysql.service`.
После запуска MySQL API автоматически не запустился и оставался выключенным
почти четыре суток. Текущая исправность API при первой проверке скрывала этот
исторический простой.

## Установленные факты

- Пользователь подтвердил APK 1.0.7 (22), номер `+7 999 888-77-66`, код `4455`
  и вход кнопкой «У меня нет VK, MAX, Telegram».
- В локальном `taxi-grahovo-1.0.7-22-rustore.apk` присутствует адрес
  `https://api.taxigr.ru`; адрес временного туннеля не обнаружен.
- SHA-256 APK:
  `AF5AD6A6CC174B56D6E04296B4477E9B1075E30F170BF9140465B8D1939ED774`.
- В действующем API запрос кода для этого номера обходит SMS-провайдера.
  Вход на рабочем API проверен дважды; 502 не воспроизведён.
- Полная проверка `npm run check:store-review -- https://api.taxigr.ru` прошла:

  | Этап | Ответ |
  | --- | --- |
  | Готовность API и БД `/health/ready` | HTTP 200 |
  | Запрос кода `/v1/auth/phone/start` | HTTP 200 |
  | Подтверждение `4455` `/v1/auth/phone/verify` | HTTP 200 |
  | Загрузка профиля `/v1/me` | HTTP 200 |
  | Обновление сессии `/v1/auth/refresh` | HTTP 200 |
  | Загрузка профиля с обновлённой сессией `/v1/me` | HTTP 200 |

- Аккаунт имеет только роль `passenger`, профиль заполнен. Реальные заказы при
  диагностике не создавались, сообщения через SMS или мессенджеры не отправлялись.
- Последний production workflow для `18c681a3d039c0352a358cc6f08bf3f15e6b2eee`
  успешно завершился 6 сентября 2026 в 00:10 UTC. Это не доказывает доступность
  сервера в момент проверки модератором.

## Production-логи и причина

После предоставления SSH-доступа прочитаны журналы nginx, systemd, apt,
unattended-upgrades и события авторизации из production MySQL.
Все времена ниже — **UTC** (для Самары прибавить четыре часа).

| Время | Событие и источник |
| --- | --- |
| 2 сентября 06:22:50 | `/usr/bin/unattended-upgrade` начал обновление пакетов MySQL; `/var/log/apt/history.log`. |
| 2 сентября 06:22:52 | systemd остановил `taxigr-api.service`, приложение получило SIGTERM; затем остановлен MySQL. |
| 2 сентября 06:23:08 | MySQL снова запущен. API остался выключенным. |
| 5 сентября 08:27:50 | Android-клиент `okhttp/4.12.0` получил 502 на `/v1/auth/max/start`. |
| 5 сентября 08:28:02 | Тот же клиент получил 502 на `/v1/auth/phone/start`. nginx записал `connect() failed (111: Connection refused)` для `127.0.0.1:4100`. |
| 6 сентября 00:03:17 | API запущен следующей выкладкой, согласно `journalctl -u taxigr-api.service`. |

API простаивал **3 суток 17 часов 40 минут**. В таблице `auth_attempt_events`
нет обработанных попыток тестового номера за этот период: nginx не мог передать
запрос остановленному процессу. Успешные попытки есть до простоя, 31 августа,
и во время нашей диагностики 7 сентября.

Проблема находится в unit-файле: `Requires=mysql.service` распространяет остановку
MySQL на API, но отдельный последующий запуск MySQL не поднимает API обратно.
`Restart=on-failure` не устраняет остановку, выполненную самим systemd из-за
зависимости. Семантика сверена с документацией
[systemd 255: зависимости](https://github.com/systemd/systemd/blob/v255/man/systemd.unit.xml)
и [перезапуск служб](https://github.com/systemd/systemd/blob/v255/man/systemd.service.xml).

Лог nginx не содержит тело запроса или модель телефона: принадлежность конкретного
запроса модератору RuStore однозначно не идентифицирована. Но серверный отказ
Android-входа с HTTP 502 и причина продолжительного простоя подтверждены.

## Изменения по результатам диагностики

В `deploy/taxigr-api.service` заменено `Requires=mysql.service` на
`Wants=network-online.target mysql.service`, сохранён порядок запуска `After`.
API продолжает работать во время обслуживания базы, а пул подключений восстанавливает
соединения после её возврата. Запросы, которым нужна БД, во время самого обслуживания
могут временно завершаться ошибкой; многодневный простой после запуска БД устранён.

7 сентября в 00:53 UTC исправление применено к
`/etc/systemd/system/taxigr-api.service` через `systemctl daemon-reload`.
Проверены действующие зависимости: MySQL есть в Wants и отсутствует в Requires.
PID API сохранился — рабочие API и MySQL для применения исправления не перезапускались.
Резервная копия:
`/etc/systemd/system/taxigr-api.service.rustore-backup-20260907T005331Z`.

Добавлена проверка `deploy/check-service-dependency.py`. На production systemd 255
она создала временные службы с `sleep`, воспроизвела остановку/запуск условной БД
и доказала: старый API остаётся выключенным, исправленный сохраняет тот же процесс.
Тестовые службы удалены. Реальная база при проверке не останавливалась.
Дополнительно установленная production-версия mysql2 успешно восстановила
собственное диагностическое подключение после его закрытия сервером.

Добавлена команда `check:store-review` и её вызов в production workflow после
активации релиза. Она проверяет полный вход и восстановление сессии и завершает
workflow с ошибкой при сбое. Это проверка после выкладки, она не делает откат
релиза и не устраняет простой сервера сама по себе. Изменения подготовлены
локально; workflow на GitHub ещё не обновлён. Unit-файл исправлен и локально,
и на production. Для сохранения исправления при следующих выкладках изменения
репозитория должны войти в `main`.

Проверка не выводит токены и тела ответов, не повторяет запросы авторизации
автоматически и использует только выделенный аккаунт модерации. Если кто-то
недавно запросил код и не завершил вход, возможен HTTP 429: дождаться окончания
лимита повторного запроса перед следующим запуском.

После применения исправления повторный полный вход на публичном API прошёл:
все шесть запросов вернули HTTP 200. 19 связанных тестов, TypeScript и ESLint
также прошли. Пересборка APK для устранения этого серверного дефекта не нужна.
Запуск APK на указанном Xiaomi не проверен: подключённого устройства и эмулятора
в рабочем окружении нет.
