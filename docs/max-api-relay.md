# Экспериментальный резервный канал MAX

Добавлен второй резерв VK и общий механизм переключения. Актуальная схема
двух каналов и результаты новых проверок описаны в [reserve-channels.md](reserve-channels.md).

По умолчанию выключен. В production не включался. Основной API имеет приоритет;
после сетевой ошибки, таймаута 3 секунды или HTTP 502/503/504 клиент передаёт тот же
запрос через фиксированный личный диалог бота со служебным аккаунтом. Через
15 секунд клиент снова пробует обычный API. Ошибки авторизации и HTTP 429 не
обходятся. Если сам процесс API или его база остановлены, этот канал тоже не
работает: он помогает при недоступности обычного соединения с работающим сервером.

Запросы и ответы сжимаются и шифруются NaCl box. Для каждого запроса создаётся
отдельная пара ключей, токен пользователя находится внутри шифротекста. Сервер
использует существующие маршруты и проверки прав пассажира, водителя и
администратора. Срок жизни запроса ограничен. Мутации получают общий для двух
каналов идентификатор; миграция 066 сохраняет результат для защиты от повторного
выполнения при потерянном ответе. Записи удаляются через два дня. Повтор выдачи
результата проверяет действительность сессии.

Socket.IO остаётся основным каналом событий. При разрыве используется опрос
авторизованного `/v1/realtime/events` примерно раз в 6 секунд. Чат и поездка
разделяют одно соединение пользователя. После перезапуска сервера или пропуска
буфера вызывается обычная повторная загрузка состояния. Обновления разных
пользователей разделяются серверными комнатами, как в Socket.IO.

## Настройка отдельного стенда

1. Применить миграции, включая `066_transport_request_replays.sql`.
2. Использовать отдельный технический бот и один разрешённый личный диалог.
   `MAX_RELAY_CHAT_ID` и `MAX_RELAY_SERVICE_USER_ID` должны указывать на него.
   Сервер проверяет соответствие диалога до первой отправки. Все пакеты
   отправляются только в этот диалог с `notify: false`.
3. Один раз создать серверную пару ключей через
   `createRelayKeyPair` из `src/api/max-relay-protocol.ts`. Секретный ключ в Base64
   хранить только в `MAX_RELAY_SECRET_KEY`; публичный — в
   `EXPO_PUBLIC_MAX_RELAY_PUBLIC_KEY`. Сохранить пару между перезапусками.
4. Указать одинаковые `MAX_RELAY_CHANNEL` / `EXPO_PUBLIC_MAX_RELAY_CHANNEL`,
   идентификаторы диалога и служебного пользователя. Серверу нужен
   `MAX_RELAY_BOT_TOKEN`. Не использовать секрет сервера в клиентской конфигурации.
5. Включить `MAX_RELAY_ENABLED=1` на стенде, а клиентскую опцию
   `EXPO_PUBLIC_MAX_RELAY_ENABLED=1` — в отдельной тестовой сборке.

Публичные Expo-переменные входят в сборку. Если для нативной тестовой сборки
задан `EXPO_PUBLIC_MAX_RELAY_BOT_TOKEN`, этот токен можно извлечь из приложения:
шифрование содержимого пакетов не скрывает полномочия самого бота. Проверки
получателя в нашем коде не ограничивают возможности владельца извлечённого
токена. Поэтому текущий общий бот не должен попадать в публичный релиз.

такси в браузере, три независимые сессии: пассажир, водитель и супер администратор.

## Практические границы

- Веб-стенд использует **локальный** CORS-шлюз к настоящему MAX API. Он не является
  готовым резервом для публичного сайта. Прямой доступ из браузера к MAX API
  не прошёл CORS-проверку. Нельзя публиковать этот шлюз или зависеть в нём от
  доступности основного API.
- Нативная работа на Android/iOS и сеть оператора с действующими белыми списками
  ещё не подтверждены. MAX требует доверия сертификатам Минцифры; Node-стенд
  использовал существующий доверенный корневой сертификат через
  `NODE_EXTRA_CA_CERTS`, без отключения проверки TLS. В нативной сборке необходимо
  отдельно проверить цепочку доверия. Одна сборка JS не доказывает доступность
  сети на устройстве.
- Это транспорт JSON API и событий при открытом приложении. Загрузка карт,
  фотографий по URL и доставка системных push в фоне используют существующие
  каналы и не становятся автоматически доступными через MAX. Проверенные
  уведомления внутри открытого приложения доставляются через опрос событий.
- Общий диалог, ограничения Bot API и последовательная отправка создают очередь.
  Нет гарантии задержки до 10 секунд при массовой нагрузке. Буфер событий —
  5 минут / 3000 событий; история MAX читается страницами по 100 с ограниченным
  окном обработки. Публичное включение требует нагрузочного теста и отдельного
  решения для выдачи клиентских полномочий, медиа и фоновой доставки.

Документация MAX: https://dev.max.ru/docs-api/methods/GET/messages
