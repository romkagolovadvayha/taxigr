# Основной API, VK и MAX

Добавлен общий резервный транспорт для приложения такси. Основной HTTP API и
Socket.IO сохраняют приоритет. Если обычное соединение не отвечает за 3 секунды
либо возвращает сетевую ошибку / HTTP 502, 503, 504, клиент использует резерв.
VK и MAX проверяются параллельно, без отправки заказа во время проверки.
Проверки ограничены четырьмя секундами и объединены для одновременных запросов.
Проверяется полный шифрованный обмен с `/v1/transport-health`: доступность
самого API мессенджера не доказывает возможность доставки ответа сервера.
Быстрый доступный канал запоминается примерно на минуту.

Если резерв потерял ответ, тот же запрос отправляется через другой резерв.
При двух каналах действие получает до 8 секунд на первую попытку,
чтение данных — до 20 секунд, вторая попытка — до 30 секунд. Это позволяет
очереди одновременных запросов админки завершить загрузку без ложного отказа
здорового канала. Большие JSON-запросы имеют увеличенный бюджет.
Недоступный канал понижается в приоритете на 30 секунд. VK Flood control
останавливает запросы этого транспорта на пять минут без немедленных повторов;
worker тоже выдерживает паузу, чтобы не продлевать ограничение. Через 15 секунд
приложение снова пробует обычный API. Успешные запросы в резерве не откладывают
эту проверку бесконечно.

Корректный ответ backend, включая 401, 403, 429 и 500, завершает попытку:
смена канала не обходит ограничения прав и не скрывает ошибку сервера.
Отмена клиентом останавливает последующие попытки. Отключение одного
потребителя чата не разрывает общее соединение поездки.

## Повторные действия и права

Всем попыткам одной мутации соответствует один `X-Taxi-Request-Id`.
Журнал `transport_request_replays` из миграции 066 объединяет запросы,
поступившие через HTTP, VK или MAX. Сессия и тело запроса сохраняются между
каналами. Действие выполняется один раз; повтор получает сохранённый результат.
При выдаче сохранённого результата действительность сессии проверяется снова.

VK и MAX используют один протокол сжатия, NaCl box, фрагментации, срока жизни
и проверки ответов. Клиент создаёт отдельный ключ для каждого запроса.
Секретный ключ сервера остаётся на backend. Запросы проходят существующие
маршруты приложения с обычной проверкой роли и прав пользователя.

`/v1/realtime/events` доставляет события только комнатам авторизованного
пользователя. Общая реализация используется пассажиром, водителем и админкой.
При возврате Socket.IO опрос событий прекращается.

## Конфигурация

Оба канала по умолчанию выключены. Новая интеграция не публиковалась.
Параметры перечислены в `.env.example`:

| Назначение | MAX | VK |
|---|---|---|
| Включение backend | `MAX_RELAY_ENABLED=1` | `VK_RELAY_ENABLED=1` |
| Токен отдельного бота | `MAX_RELAY_BOT_TOKEN` | `VK_RELAY_BOT_TOKEN` |
| Фиксированный диалог | `MAX_RELAY_CHAT_ID` | определяется служебным пользователем |
| Сообщество | — | `VK_RELAY_GROUP_ID` |
| Служебный пользователь | `MAX_RELAY_SERVICE_USER_ID` | `VK_RELAY_SERVICE_USER_ID` |
| Имя канала протокола | `MAX_RELAY_CHANNEL` | `VK_RELAY_CHANNEL` |
| Секретный ключ сервера | `MAX_RELAY_SECRET_KEY` | `VK_RELAY_SECRET_KEY` |

Клиентские параметры имеют префиксы `EXPO_PUBLIC_MAX_RELAY_` и
`EXPO_PUBLIC_VK_RELAY_`. Вместо секретного серверного ключа клиент получает
`PUBLIC_KEY`. В тестовой нативной конфигурации токен бота задаётся как
`BOT_TOKEN`. Этот токен извлекается из приложения: согласие хранить его в
сборке не делает его секретным. Проверки адресата в клиентском коде не
ограничивают полномочия человека, получившего токен. До публичного включения
нужны отдельные технические боты и решение по выдаче клиентских полномочий.

Служебный VK-пользователь для этого теста явно указан пользователем:
Роман Мещеряков, ID 33610634, сообщество «Такси Грахово» 193790756.
MAX использует ранее подтверждённый отдельный служебный диалог.
Сообщения другим аккаунтам и звонки не выполняются. Получатели зафиксированы
в конфигурации транспортов; браузерный стенд дополнительно проверяет их в шлюзе.

`GATEWAY_URL` разрешён только для loopback HTTP и нужен локальному веб-стенду.
Токены в браузерный тестовый bundle не включаются, запросы идут к реальным API
через локальные CORS-шлюзы. Это не готовое решение для публичного веб-сайта.
Нативный транспорт обращается непосредственно к соответствующему API;
для MAX необходимо отдельно обеспечить доверие его цепочке TLS-сертификатов.
Проверка TLS нигде не отключается.

## Проверка 12.11.2026

В `artifacts/dual-relay-integration-2026-11-12/` сохранены результаты 49 успешных
проверок на настоящих VK/MAX API и отдельной локальной базе:

- Полный цикл заказа и двусторонний чат через каждый резерв.
- Фрагментированный запрос с 16 КБ случайных данных через каждый канал.
- VK выполнил создание заказа, ответ был потерян: MAX вернул тот же заказ;
  в базе осталась одна запись.
- События водителя и администратора, настройки админки и заказ супер
  администратора в роли пассажира.
- Запрет чужой роли, недействительная сессия, недоступность всех каналов,
  восстановление каждого резерва и автоматический возврат основного API.

Доступность сервисов при белых списках принята как условие пользователя;
проверки моделируют разрыв обычного соединения и каждого резерва отдельно.
Проверка физического устройства в ограниченной сети не заявляется.
Обработка фото по URL, загрузка карты и системные push в фоне пока используют
прежние каналы. Если сам backend или база остановлены, оба резерва тоже
перестают обрабатывать запросы.

## Нагрузка

### Повторная проверка и объединение чтений, 12.11.2026

Новый worker сообщает о поддержке пакетных чтений в необязательном поле
`features.readBatch` и в `/v1/transport-health`. После подтверждения клиент
собирает до 10 одновременных GET за 25 мс в один зашифрованный пакет.
Аккаунты и сессии разделены; действия изменения данных идут отдельно.
`POST /v1/transport/read-batch` принимает только относительные GET-пути,
проверяет каждое чтение через исходный маршрут с его правами и ограничениями.
Пакет чтений не записывается в журнал повторов изменяющих операций.

Старые клиенты продолжают пользоваться прежними маршрутами и форматом пакетов.
С новым клиентом и старым сервером чтения отправляются отдельно; после отката
сервера ответ 404/405 отключает пакетный режим и возвращает отдельные GET.
Отказы 401/403/429 и ошибки сервера не обходятся повторной отправкой.

Экран заказа и чат используют одно соединение в пределах сессии приложения,
в том числе без включённых резервов. Событие для нескольких пересекающихся
групп получателей доставляется аккаунту один раз. При сбое доставки worker
повторяет сохранённый ответ, сохраняя уже загруженные фрагменты; повторно
выполнять действие для очередной попытки доставки не требуется.

Проверки и замеры: `artifacts/relay-request-review-2026-11-12/`.
Через настоящий `api.vk.ru` три чтения получили 200 в одном `messages.send`
за 1265 мс, с одним `messages.getById` на стороне клиента. У worker остаются
запросы истории и редактирование ответа; это не один суммарный API-вызов.
При открытии веб-чата: одна загрузка истории и ноль новых WebSocket.
Эти замеры не являются многопользовательским нагрузочным испытанием.
Повторная прямая проверка MAX также прошла: три чтения получили 200 за
1062 мс, один POST `/messages` и один GET `/messages` на стороне клиента.
Проверка служебного адресата прошла, worker после проверки остановлен.

При последующей одновременной проверке трёх веб-сессий VK реально вернул код 9:
`Flood control: too much messages sent to user`. Поэтому 49 успешных
последовательных сценариев не доказывают пригодность VK для постоянной
нагрузки в одном диалоге. Обработка этого случая дополнена паузой и выбором
резерва по полному ответу worker, а не только по доступности API.

Лимит VK для ключа сообщества — 20 API-вызовов в секунду, отдельные методы
ограничиваются дополнительно. MAX указывает 30 API-вызовов в секунду и не
более двух новых сообщений в секунду в один диалог. Один запрос приложения
расходует несколько API-вызовов. Эти ограничения не складываются в
«50 действий в секунду» и не гарантируют задержку до 10 секунд при массовой
нагрузке. Очередь внутри одного клиента не является глобальным ограничителем
для всех установок приложения с одним токеном.
