# Резервный HTTP API Prostoj

Порядок клиента: основной API → HTTPS-прокси Prostoj → резерв VK/MAX.
Боты продолжают обращаться непосредственно к своим API. Если backend или его
база остановлены, все пути к нему перестают выполнять заказы.

Публичный резерв: `https://hooks.prostoj.store/taxigr`.
Для сборок с `EXPO_PUBLIC_API_URL=https://api.taxigr.ru` он включается по
умолчанию. `EXPO_PUBLIC_FALLBACK_API_URL` переопределяет адрес; пустое значение
отключает HTTP-резерв. Loopback разрешён только локальному веб-стенду.
Токенов и пароля HTTP-прокси в клиенте нет.

Небольшой запрос ждёт основной путь до 3 секунд, прокси до 5 секунд; большие
загрузки получают до 12 секунд на HTTP-путь. При успехе прокси боты не вызываются.
Вышедший из строя HTTP-путь проверяется снова через 15 секунд одним из
последующих запросов. Успешные запросы через резерв не отодвигают возврат на
основной. Отмена пользователем и структурированные прикладные ошибки, включая
401/403/409/429, не вызывают повтор через следующий путь.

Изменяющий запрос сохраняет один `X-Taxi-Request-Id` на всех путях. При выпуске
клиента backend должен уже содержать middleware `transport-idempotency` и
миграцию `066_transport_request_replays.sql`. Отдельные механизмы
`idempotencyKey` заказа и `clientMessageId` чата сохраняются.
Расчёт `/v1/quotes` и пакет чтений не записываются в журнал повторов:
они возвращают свежие данные и не изменяют заказ.

WebSocket заказа и чата переключается вместе с HTTP-каналом; при недоступности
WebSocket события доступны через прежний `/v1/realtime/events`. Ссылки на свои
фотографии и вложения используют активный HTTP-прокси. Внешние изображения не
переписываются. Пакетные чтения через ботов остаются согласуемой возможностью.
Сохранение полученного ответа для работы без сети выполняется в фоне;
отображение свежих данных не ждёт записи на диск.

## Серверы

### Порядок выпуска и совместимость

Сначала выкладывается backend с миграцией `066_transport_request_replays.sql`,
потом веб и новые приложения. Миграция добавляет отдельную таблицу и не меняет
поля старых заказов. Старые клиенты не передают `X-Taxi-Request-Id`; middleware
их пропускает без изменения прежних правил. Полные API-циклы исходных клиентов
1.0.25 (`5495978`) и 1.0.28 (`d83fc5a`), смешанные пары и старые Socket.IO
события проверены на обновлённом backend. Протоколы старых клиентов сохраняются;
резервные пути появляются после обновления клиента.

Серверный архив устанавливает только `server/package.json`. В нём должны быть
`base64-js`, `fflate`, `tweetnacl`. Корневой `node_modules` релиза ссылается на
`server/node_modules`, чтобы общие файлы `src/api` находили эти пакеты.
`scripts/check-server-release.mjs` проверяет эту схему в отдельной временной
директории. CI запускает проверку, а deploy выполняет
`server/scripts/check-runtime.ts` до миграций и активации релиза.

CI передаёт настройки VK/MAX одновременно в публичную сборку и в окружение
сервера. По умолчанию оба канала выключены. Для включения нужны переменные
`VK_RELAY_*`/`MAX_RELAY_*` из workflow: канал, служебный адресат, публичный ключ,
токен и отдельный секретный ключ сервера. Секретный ключ не включается в клиент.
Включённый канал с неполными настройками останавливает выпуск до активации.
Проверенные production-настройки на 12 ноября ещё не включали VK/MAX и не
содержали миграцию 066: локальный тест сам по себе не включает эти функции на
продакшене. Используйте отдельный production-канал и ключ, не канал тестового
стенда, чтобы два обработчика не отвечали на один пакет из разных баз.

При запросах через бота внутренний адрес для ограничения частоты вычисляется
по проверенной JWT-сессии. Обновление токена и смена VK/MAX сохраняют один
лимит пользователя; другие пассажиры не расходуют его квоту. Анонимные и
недействительные сессии остаются в общем ограниченном пуле. Пользовательские
адреса или заголовки из пакета в этот расчёт не принимаются.

Новому Android/iOS клиенту требуется полноценная сборка с локальным нативным
модулем. Перед публикацией в магазине увеличьте версию и номер сборки;
проверочный APK с прежним номером не является новой отправленной версией.
Предрелизный протокол: `artifacts/release-compatibility-2026-11-12/report.html`.
В нём 1620 успешных тестов, семь полных циклов совместимости, чистый серверный
runtime и подписанная Android APK-сборка. Наличие модуля MAX, данных карты и
шрифтов проверено в APK; запуск на устройстве и нативная iOS-сборка не выполнялись.

### Параллельные действия приложения и ботов

Протокол следующей проверки: `artifacts/concurrency-2026-11-12/report.html`.
Матрица содержит 27 сценариев: создание заказов, повтор одной операции,
конкуренция водителей, очередь, отмена, выход с линии, ожидание, изменение
маршрута и цены, чат, предзаказы и оценки. Локальная часть из 26 сценариев
повторяется ещё три раза; внешние VK/MAX-пакеты при повторах не отправляются.
В отдельном сценарии реальные служебные VK/MAX и HTTP конкурируют за создание
и принятие: блокировка строки удерживается до прихода всех трёх запросов.

Повторное принятие уже назначенного этому же водителю активного заказа теперь
возвращает его без повторного назначения. Другой водитель по-прежнему получает
409. Позднее `paymentReceived:true` сохраняет подтверждение оплаты уже
завершённой поездки, не повторяя завершение, расчёт и продвижение очереди.
Обычные бот-кнопки и текстовое оформление используют ту же проверенную
идентичность пользователя для ограничения частоты, что и резервные каналы.

Транзакция оценки сохраняет блокировку заказа, заранее блокирует обе строки
пользователей в стабильном порядке и использует READ COMMITTED. Это убирает
взаимные блокировки при вставке FK и пересчёте среднего балла. Уникальность
оценки по заказу и стороне сохраняется. Проверены одновременные оценки разных
пользователей и 16 оценок одному водителю / пассажиру с проверкой количества
и среднего значения.

На Prostoj существующий TLS/SNI-роутер направляет `hooks.prostoj.store` на
`127.0.0.1:18483`. Новый listener принимает PROXY protocol, обслуживает только
фиксированные `/taxigr/v1/`, `/taxigr/uploads/`, `/taxigr/socket.io/` основного
API и не принимает произвольный upstream. `/v1/internal` и `/v1/webhooks`
закрыты на резерве. Остальные пути hooks передаются прежнему listener 1443.
Проверка TLS основного сервера включена, автоматические повторы POST в nginx
выключены, личные ответы не кэшируются.

Шаблон: `deploy/prostoj-fallback.nginx.conf`. Секретный файл
`/etc/nginx/taxigr-fallback-upstream-key.conf` существует только на сервере,
доступен root и добавляет приватный заголовок для основного nginx. Ключ хранится
в `/opt/taxigr-fallback/upstream-key`, не возвращается клиенту и не записывается
в журналы.

На основном сервере `/etc/nginx/conf.d/taxigr-fallback-client-map.conf`
сохраняет существующую обработку PROXY protocol. IP клиента из HTTP-заголовка
принимается только от двух адресов Prostoj и с верным приватным ключом.
Иначе используется адрес исходного соединения. Заголовок ключа удаляется перед
передачей приложению. Шаблон — `deploy/taxigr-prostoj-realip.conf`;
`__SERVER_PROXY_KEY__` необходимо заменить приватным ключом при установке,
сохранив права 0600. `remote-deploy.sh` сохраняет использование установленной
карты IP при обновлениях. Обычные пользователи и CONNECT-прокси с тем же внешним
IP не могут подменить адрес без серверного ключа.

Резервные копии конфигураций на серверах созданы перед настройкой.
Не отключайте существующий PROXY protocol и не заменяйте его общим доверием
входящему `X-Forwarded-For`: серверы используют TLS-маршрутизаторы на loopback.

## Проверка 12 ноября 2026

Повторная расширенная проверка: `artifacts/transport-recheck-2026-11-12/report.html`
и `receipt.json`. Суммарно прошли 1605 тестов: 1462 модульных, 115 API/SQL,
16 рассылок с подменённой отправкой, 6 реальных HTTP/VK/MAX и 6 полных
сценариев заказа. Все 143 сценария, пропускаемые обычным запуском без
интеграционных флагов, выполнены отдельными прогонами на тестовых базах.

Дополнительно проверены гонка восстановления основного API, отмена до отправки
и во время чтения ответа, заголовки `Headers`/массивом пар и потеря успешного
ответа прокси без дублирования заказа. Веб-проверка включает полный заказ,
двусторонний чат, оплату, повторное принятие, отмену и сохранение настройки
админки после перезагрузки. На размерах 390×844 и 360×640 проверенные экраны
заказа не увеличивали размеры страницы. Карта и маршрут отображались при
отключении обоих HTTP-путей и блокировке внешних HTTPS-запросов в тестовой вкладке;
после восстановления повторный расчёт прошёл через основной API.

При смене публичных переменных окружения перед проверкой Expo экспортируйте
с `--clear`: кэш Metro может сохранить прежний адрес резерва. Это относится
к сборке; настройка адресов через runtime-переменные после экспорта невозможна.
Android/iOS проверены JS-экспортом, без запуска на устройствах и без проверки
операторских белых списков. Новые клиентские изменения не опубликованы.

Артефакты: `artifacts/prostoj-fallback-2026-11-12/`.

- HTTPS, CORS, публичный API, Socket.IO и отказ неправильной авторизации через
  настоящий Prostoj проверены; прежние `/healthz`, `/relay` и `/` hooks сохранили
  свои коды ответа.
- Передача IP проверена двумя уникальными запросами и журналами обоих
  серверов; поддельный `X-Forwarded-For` игнорируется.
- На отдельной базе проверены три роли, возврат на основной путь, потеря
  успешного ответа с сохранением единственного заказа и реальный VK/MAX после
  отказа обоих HTTP-путей. Технические пакеты отправлялись только ранее
  согласованным служебным адресатам.
- В браузере три обновлённые роли работали через локальный аналог прокси при
  отключённом основном API, без запросов к ботам. В другом пользовательском
  preview оставалась прежняя версия без HTTP-резерва; её запросы отражены
  отдельно в общих счётчиках стенда.
- Проверены типизация, линтер, модульные сценарии и JS-экспорт web/Android/iOS.
  Запуск на физических устройствах и в ограниченной сети не выполнялся.

Серверный прокси включён. Изменения клиента и backend в этом шаге не
публиковались, новые версии в магазины не отправлялись.
