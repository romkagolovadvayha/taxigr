# Проверка маршрутов «Такси Грахово» — 8 сентября 2026

> Это исходный отчёт до исправлений. Все три описанные ниже ошибки исправлены локально и повторно проверены: [результаты исправлений](2026-09-08-routing-fixes.md). Исходные измерения сохранены для сравнения.

Полностью корректной маршрутизацию считать нельзя: воспроизведены три существенные проблемы. Обычные дорожные маршруты, тарифы по текущим правилам и обработка сетевых сбоев работают в проверенных сценариях.

## Среда и объём проверки

- Проверен текущий локальный код без изменений логики приложения.
- Прочитана требуемая документация Expo SDK 57.
- Создана отдельная база taxi_route_audit_20260908; применены все 43 миграции. API работал на 4110, интерфейс на 8090. Рабочие ключи мессенджеров, SMS и push в тестовый API не передавались.
- Маршруты реально запрашивались через API приложения у публичного OSRM, который также указан в GitHub workflow деплоя. Развёрнутая конфигурация сервера отдельно не проверялась. Предусмотренный Docker-конфигурацией региональный OSRM не запускался: Docker daemon локально недоступен.
- 311 обычных тестов, 31 интеграционный тест и 6 дополнительных тестов отказоустойчивости прошли: всего 348.
- TypeScript и штатный Expo lint прошли. Обычная команда npm не запускается из-за повреждённого глобального npm-cli.js, поэтому использованы локальные CLI через node. Дополнительный широкий eslint по всей папке нашёл ошибки в служебных/сгенерированных файлах; он не эквивалентен штатному Expo lint.
- Выполнены 47 запросов матрицы: 36 сочетаний шести адресов, 7 сценариев с остановками и 4 отрицательных проверки. Дополнительно проверены 2 дальних маршрута, 5 поисковых запросов, маршрут между разными домами ГАР и 3 состояния навигации водителя.
- В браузере открыты приложение и экран входа. Ручная проверка пассажирского экрана пока не выполнена: автоматическая проверка разрешений остановила ввод тестового телефона и согласие в форме, ожидается разрешение пользователя. Результаты ниже получены через реальные API-запросы и проверку кода, а не через клики по экрану заказа.

## 1. Высокий приоритет: дома из ГАР не имеют индивидуальных координат

В справочнике 4 266 домов, но лишь 40 уникальных пар координат. В частности, 1 395 домов Грахово используют одну точку 56.0457978, 51.9607416. Номер дома делает такой адрес «точным» для интерфейса, хотя его координаты приблизительные. Форматирование подсказок не показывает примечание о приблизительной точке.

Воспроизведение:

1. GET /v1/addresses/preview?query=Грахово Советская 1.
2. GET /v1/addresses/preview?query=Грахово Береговая 32.
3. Подать два полученных адреса в POST /v1/routes/preview.

Оба дома получили одинаковые координаты. API вернул source=estimate, 800 м, 300 с, пустую геометрию и 150 ₽. Сервис не рассчитывает дорогу от одного реального дома до другого. Для других пар приблизительные точки также влияют на подачу и километраж.

Причина: [построение справочника](../../src/data/grahovo-address-directory.ts#L291), [ранний возврат локального совпадения](../../server/geocoding.ts#L476), [критерий точности подсказки](../../src/screens/passenger/address-search-screen.tsx#L143), [выбор адреса](../../src/screens/passenger/address-search-screen.tsx#L414).

Исправление должно разделить существование адреса в ГАР и точность координат, получать точку конкретного дома либо просить указать её на карте. Одного изменения коэффициента расстояния недостаточно.

## 2. Высокий приоритет: навигация возвращает водителя к пройденной остановке

Создан локальный тестовый заказ A → B → E, водитель принял его, прошёл статусы до in_progress. Далее отправлялись реальные запросы /v1/driver/orders/:id/route с разными координатами водителя.

| Положение водителя | Ответ API |
|---|---|
| У подачи A | 2 337 м, 299 с, OSRM, 51 точка геометрии |
| На первой остановке B | 2 682 м, 524 с, estimate, геометрия отсутствует |
| Уже в конечной точке E | Ещё 3 603 м, 449 с, OSRM: маршрут снова через B |

Причина: [обработчик навигации](../../server/routes.ts#L4941) каждый раз передаёт все исходные destinations; индекс пройденной остановки в модели не хранится. Это также прямо отражено в [логике статусов точек](../../src/domain/ride-state.ts#L44). После проверки тестовая поездка завершена.

Нужно хранить прогресс остановок и рассчитывать только оставшуюся часть маршрута. Простого удаления повторяющихся координат недостаточно: маршрут с намеренным возвращением A → B → A должен сохраняться.

## 3. Высокий приоритет: нулевой участок портит весь маршрут с остановками

Все шесть диагональных пар матрицы вернули 800 м и 5 минут при совпадающих координатах. Отдельная минимальная стоимость поездки может быть бизнес-правилом, но перенос этих минимальных метров и минут в каждый нулевой участок многоточечного маршрута и потеря всей геометрии некорректны.

| Ввод | Расстояние | Время | Эконом / детский | Геометрия |
|---|---:|---:|---:|---|
| A → B → E | 2 337 м | 299 с | 240 / 310 ₽ | 51 точка OSRM |
| A → B → B → E | 3 137 м | 599 с | 330 / 400 ₽ | Пустая, estimate |

Одна повторённая остановка добавила 800 м, 5 минут и 90 ₽. [parseOsrmRoute](../../server/routing.ts#L142) отвергает нулевые расстояние/время; [estimateRoute](../../server/routing.ts#L89) заменяет их минимумом; [сборка маршрута](../../server/routing.ts#L244) удаляет геометрию всех участков при одной оценке.

Нужно корректно обрабатывать нулевые участки, отдельно определять стоимость остановки и проверять случай одинаковых адресов в UI/API. Исправление не должно склеивать разные дома только по одинаковым приблизительным координатам.

Цена Можга → Грахово выше обратного направления по существующей логике: в межгороде к поездке добавляется подача машины от базы в Грахово. Например, A → D: 56 416 м и 1 700 ₽; D → A: 56 402 м поездки + 56 400 м подачи, 3 390 ₽. Это соответствует коду, а корректность самого бизнес-правила требует решения владельца. Для районных поездок такая подача в цену не включается.
